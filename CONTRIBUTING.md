## Getting Started

### Prerequisites

- [Go](https://go.dev/dl/) 1.23 or later (see `go.mod` for the current version)
- [Terraform](https://developer.hashicorp.com/terraform/downloads) 1.1+
- [golangci-lint](https://golangci-lint.run/welcome/install-locally/)
- [mockery](https://vektra.github.io/mockery/) (for generating mocks)
- A configured [CDP API access key](https://docs.cloudera.com/cdp-public-cloud/cloud/cli/topics/mc-cli-generating-an-api-access-key.html) (for acceptance tests)

### Fork and Clone

1. Fork the repository on GitHub.
2. Clone your fork locally:

   ```bash
   git clone https://github.com/<your-username>/terraform-provider-cdp.git
   cd terraform-provider-cdp
   ```

3. Add the upstream remote:

   ```bash
   git remote add upstream https://github.com/cloudera/terraform-provider-cdp.git
   ```

## Development Setup

### Build the Provider

```bash
make build
```

This runs code generation, formatting, vetting, and compiles the binary.

### Install Locally

To test the provider against your own Terraform configurations:

```bash
make install
make install-terraformrc
```

This installs the provider binary and sets up `~/.terraformrc` to point Terraform at your local build.

### Useful Make Targets

| Command                | Description                                      |
|------------------------|--------------------------------------------------|
| `make build`           | Generate, format, vet, and compile               |
| `make test`            | Run unit tests                                   |
| `make testacc`         | Run acceptance tests (requires CDP credentials)  |
| `make lint`            | Run golangci-lint                                |
| `make fix-lint`        | Run golangci-lint with auto-fix                  |
| `make fmt`             | Format Go and Terraform code                     |
| `make generate`        | Run `go generate`                                |
| `make docs`            | Generate provider documentation                  |
| `make check`           | Run linting, docs, deadcode analysis, and tests  |

## Project Structure

```
terraform-provider-cdp/
├── cdp-sdk-go/            # CDP SDK client
│   └── gen/               # Auto-generated API clients and models (do not edit by hand)
├── resources/             # Terraform resource and data source implementations
│   ├── environments/      # Environment resources (credential, freeipa, etc.)
│   ├── datahub/           # Data Hub resources
│   ├── datalake/          # Data Lake resources
│   ├── dw/                # Data Warehouse resources
│   ├── iam/               # IAM resources
│   └── ...
├── mocks/                 # Generated test mocks (mockery)
├── examples/              # Example Terraform configurations
│   ├── resources/         # Per-resource examples
│   └── data-sources/      # Per-data-source examples
├── templates/             # Documentation templates (tfplugindocs)
├── docs/                  # Generated documentation (do not edit by hand)
└── .github/workflows/     # CI workflows
```

### Key Conventions

- **Resource packages** live under `resources/<service>/`. Each resource or data source typically has its own sub-package.
- **Generated code** in `cdp-sdk-go/gen/` and `docs/` should not be edited manually. Regenerate with `go generate` or `make docs`.
- **Mocks** are generated by [mockery](https://github.com/vektra/mockery) based on `.mockery.yml`. Regenerate with `go generate ./...`.
- **Import ordering** is enforced by `gci`: standard library, third-party, then `github.com/cloudera/terraform-provider-cdp` prefixed imports.

## Making Changes

### Branch Naming

Create a descriptive branch from the latest `main`:

```bash
git fetch upstream
git checkout -b my-feature upstream/main
```

### Code Style

- Run `make fmt` before committing to ensure consistent formatting.
- Run `make lint` to catch issues early. The project uses [golangci-lint](https://golangci-lint.run/) with the configuration in `.golangci.yml`.
- Follow existing patterns in the codebase. If surrounding code does it a certain way, match that style.
- The provider uses the [Terraform Plugin Framework](https://developer.hashicorp.com/terraform/plugin/framework) (`terraform-plugin-framework`). Refer to its documentation when implementing new resources or data sources.

### Adding a New Resource or Data Source

1. Create a new package under `resources/<service>/`.
2. Implement the resource or data source using the Terraform Plugin Framework.
3. Register it in the provider.
4. Add example Terraform configuration under `examples/resources/` or `examples/data-sources/`.
5. Add documentation templates under `templates/resources/` or `templates/data-sources/`.
6. Run `make docs` and verify the generated output in `docs/`.
7. Write unit tests with mocked API clients (see [Testing](#testing)).

## Testing

### Unit Tests

Unit tests use mocked API clients generated by mockery. Run them with:

```bash
make test
```

Or with coverage:

```bash
make test-with-coverage
```

CI enforces a minimum coverage threshold of **40%** (excluding generated code, mocks, and SDK packages).

### Acceptance Tests

Acceptance tests run against a real CDP environment and create/destroy actual resources. They require valid CDP credentials.

```bash
make testacc
```

- Acceptance test functions must be named `TestAcc*`.
- They are skipped in CI pull request builds and only run in controlled environments.
- Always clean up resources in test teardown.

### Writing Tests

- Use the existing mock infrastructure in `mocks/`. If your resource needs a new mock, add the interface to `.mockery.yml` and run `go generate ./...`.
- For unit tests, mock the API client and verify that your resource correctly translates between Terraform state and API requests/responses.
- For acceptance tests, use the [terraform-plugin-testing](https://pkg.go.dev/github.com/hashicorp/terraform-plugin-testing) framework.

## Documentation

Provider documentation is generated by [terraform-plugin-docs](https://github.com/hashicorp/terraform-plugin-docs) from templates and schema definitions.

1. Add or update templates in `templates/`.
2. Add or update example configurations in `examples/`.
3. Run `make docs` to regenerate.
4. **Do not edit files in `docs/` directly** — they will be overwritten.

CI checks that `docs/` is in sync with the templates and schemas. If the check fails, run `make docs` and commit the result.

## Submitting a Pull Request

### Before You Submit

1. **One commit per PR.** CI enforces a single-commit policy. Squash your commits before pushing:

   ```bash
   git rebase -i upstream/main
   ```

2. **Run the full check suite:**

   ```bash
   make check
   ```

   This runs linting, documentation generation, deadcode analysis, and tests.

3. **Ensure documentation is up to date.** If you added or changed a resource, run `make docs` and include the generated changes.

### PR Guidelines

- Give your PR a clear, descriptive title.
- Describe what the change does and why in the PR body.
- Link to any related issues or discussions.
- Keep changes focused — one logical change per PR.
- Be responsive to review feedback.

### CI Checks

Every PR runs the following checks:

| Check                  | What it validates                                               |
|------------------------|-----------------------------------------------------------------|
| **Build**              | Compiles across multiple Go versions (see CI config)            |
| **Lint**               | golangci-lint passes                                            |
| **Unit tests**         | All tests pass with coverage above threshold                    |
| **Dead code analysis** | No unreachable code detected                                   |
| **Documentation**      | `docs/` matches generated output from templates and schemas     |
| **Commit count**       | PR contains exactly one commit                                  |

All checks must pass before a PR can be merged.

## Release Process

Releases are managed by the maintainers using [GoReleaser](https://goreleaser.com/) and published to the [Terraform Registry](https://registry.terraform.io/providers/cloudera/cdp/latest). Contributors do not need to worry about releases — just get your PR merged and it will be included in the next release.
